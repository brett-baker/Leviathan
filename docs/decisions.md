# Decisions made while building

One line each: the decision, then why. Newest last.

- **D6: mapped network drives are listed under Network only, not also under Local.** The spec (§7.1) says both; one entry per location keeps "follow the current folder" unambiguous and the tree shorter. Revisit when saved servers arrive.
- **D6: the tree is rebuilt (collapsed) when Favorites change.** Pinning is rare and the tree re-expands to the current folder at once; keeping expanded state through a rebuild is not worth the bookkeeping yet.
- **D6: tree rows are inserted 40 at a time with a yield between.** One big range insert took 350 to 420 ms in the list control, single inserts 70 ms for 280 rows; chunking keeps every step under the 50 ms stall budget.
- **D6: hidden folders are not shown in the tree.** Matches Explorer's navigation pane; the file view still shows them when the user asks.
- **D7: the context zone shows only actions whose command is registered.** The §6.2 table is encoded in full (ContextActions.Wanted) but a button that does nothing is worse than a missing one; the zone fills in as features land.
- **D7: Ctrl+Shift+F focuses the filter box.** Ctrl+F is reserved for search (Phase 4); filtering is per tab and clears when the tab navigates.
- **D7: Ctrl+A selects rows unless a text box has focus.** The window-level key map would otherwise swallow Ctrl+A in the address and filter boxes.
- **D8: Ctrl+click on an item toggles its selection; it does not open a folder in a new tab.** The spec (§5.1) gives Ctrl+click both jobs; multi-select is used far more. Middle-click, the command bar and the sidebar menu open folders in new tabs.
- **D8: rename runs straight on the thread pool for now.** `RenameService` is the seam: slice E4 routes it through the journaled worker so it can be undone.
- **D8: a rename box that is refused (bad name) stays open; one that fails on disk (name taken, access denied) closes with the reason in the status bar.**
- **D8: the rubber band starts on empty space, and in Details also on the blank part of a row.** Rows span the full width, so only the name and icon are reserved for drag and drop (D9).
- **D9: a drop with no copy/move engine yet is refused with a message, not done.** `UnavailableTransferService` changes nothing until E2 provides the journaled, verified implementation (spec §12.1); doing a quick unjournaled copy now would be the one path that could lose data.
- **D9: a move into the folder the items are already in is refused; a copy there is allowed.** Matches Explorer; E2 will name the duplicate with "keep both".
- **D9: a drop from another application is treated as a copy by default.** Its source volume is unknown until the drop, and copying never loses anything.
- **D9: dropping on the Favorites header pins the items instead of copying them.** The spec (§7) says any folder or file can be pinned by dragging it there.
- **D9: a plain press on an item inside a larger selection keeps the selection until the button comes up,** so the whole selection can be dragged; without a drag it then selects just that item (as Explorer does).
- **D9: mouse input in the drive scripts uses `MOUSEEVENTF_VIRTUALDESK` (0xC001).** Without it absolute moves map onto the primary monitor only, so earlier scripts relied on offsets that compensated for that.
- **D10: the hidden-item count only appears when hidden items are listed.** The listing leaves hidden items out unless asked, so they cannot be counted without a second scan; showing "· 12 hidden" for the common case would need one.
- **D10: location health shows the share and "not responding" for now.** Protocol version and round-trip time need the share health measurements (Phase 2).
- **D10: the layout switcher has Details / List / Thumbnails** (the layouts that exist) rather than the spec's Tiles; the thumbnail slider shows only in Thumbnails.
- **D11: the usage bar is one colour (used / free), not split by file type.** The per-type breakdown needs the space map's scan data (Phase 5); the folder-size store only has folder totals.
- **D11: the card shows only actions that work today:** Open terminal here and Properties. Open space map, Find duplicates and Empty Recycle Bin appear when their features land (same rule as the command bar).
- **D11: a hidden card is brought back from View > Drive summary.** The hide choice is stored per drive root in `hidden-drive-cards.json`.
- **E1: contract major bumped to 2 and the pipe name to `Leviathan.Worker.v2.`** The request gained fields and `JobKind` gained Rename and Link; a new UI must never talk to a stale v1 worker still running from before an update.
- **E1: the default conflict policy is Keep both.** It can never overwrite or lose data; Replace and Skip are explicit. "Ask each time" arrives with the conflict dialog (Phase 2).
- **E1: per-item results are kept in memory by the job host (`GetResultAsync`), not journaled yet.** Undo (E4) needs them to survive a restart and adds a journal record for them then.
- **E1: the worker validates every request at the door** (`JobRequestValidator`): a copy without a destination, a folder into itself or a bad rename name is refused before it is queued.
- **E2: copies are verified with SHA-256, not xxHash3.** Only cross-volume moves read the copy back (before the source is deleted); plain copies check the length. xxHash3 and the NAS-default verification arrive with the Phase 2 copy engine.
- **E2: a job interrupted by a crash starts again from the beginning.** The `.leviathan-part` file is overwritten, so nothing half-done is ever taken for finished; byte-level resume needs the per-file journal (Phase 2). With Keep both a restarted job may leave "name (2)" for a file that had already finished.
- **E2: shortcuts (Alt-drag) are not created yet.** The app says so and changes nothing; creating `.lnk` files needs the shell COM layer (F slices).
- **E2: drop on a folder that holds the same name keeps both by default.** Replace and Skip exist in the contract but the UI has no way to choose them until the conflict dialog (Phase 2).
- **E3: the worker now targets Windows (`net10.0-windows`) and references Leviathan.Interop.** Moving items to the Recycle Bin is `IFileOperation`, which only exists there; the Integration tests project follows.
- **E3: Del recycles at once, with no confirmation; Shift+Del asks first (default button Cancel).** Recycling is undoable, permanent delete is not (spec §12.5).
- **E3: a Recycle Bin delete reports no restore path yet.** Superseded by E4: the path is found from the `$I` record.
- **E3: on a share the trash folder is created at the share root (`\server\share\.leviathan-trash`, hidden) with a `manifest.jsonl` of original paths.** A Synology `#recycle` or QNAP `@Recycle` folder is used when the share has one, keeping the folder structure; the manifest is written either way so Restore knows the original path.
- **E4: the place of a recycled item is read from the Recycle Bin's own `$I`/`$R` files, not from `IFileOperation`.** The shell API gives no path back without a COM progress sink; the record layout (versions 1 and 2) has been stable since Vista, is what Explorer's Restore uses, and is tested against the real bin. The newest record newer than the delete wins, so an older item of the same name is never taken for it. A drive that deletes for good (a mapped network drive) leaves no record, so that delete is simply not undoable.
- **E4: undo and redo of a rename also use the worker, as a `Restore` job; the forward rename stays in-process.** A rename is one atomic metadata call, so routing it through the journal would add a pipe round trip to every F2 without making it safer; the undo entry is what is journaled. `JobKind.Rename` stays in the contract, unimplemented. (This replaces the D8 note that E4 would route the rename through the worker.)
- **E4: undo never overwrites.** If the old name or place is taken, nothing moves and the message says so; the entry stays so the user can fix the cause and press Ctrl+Z again. When only some items of a delete can be put back, those are redoable and the rest are dropped with an explanation, so one stuck item cannot block the history.
- **E4: one history for the whole app, kept 7 days, 100 entries, in `undo.json`.** Like Explorer, Ctrl+Z undoes the last thing done in any window. Writes are queued on the thread pool and atomic (temp file then rename); a damaged or unwritable file only costs the history.
- **E4: undoing a share soft delete leaves its manifest line.** The manifest records what was trashed, not what is still there; a later Restore view (Phase 2) skips entries whose trashed file is gone.
- **E4: edit keys belong to text boxes while one has the keyboard.** Del, Shift+Del, Ctrl+Z, Ctrl+Y, F2 and Ctrl+A are not turned into file commands then. Del in the filter box previously deleted the selected files (found while building undo).
- **E5: paste is a drop with the keyboard.** It uses `DropRules` and `ITransferService` unchanged: a cut counts as Shift (move), a copy as Ctrl (copy), so a copy is a copy even on one volume and pasting a copy into its own folder makes `name (2)`. Pasting a cut into its own folder is refused and keeps the clipboard.
- **E5: a started cut-paste empties the clipboard.** Like Explorer, a cut is pasted once; a second Ctrl+V would only fail on sources that are gone. A paste that did not start keeps it.
- **E5: our own clipboard writes are recognised by a marker format, not a flag.** `ContentChanged` arrives later on the dispatcher, so a flag around `SetContent` cannot tell our change from another program's (the first version lost its own list this way and a cut never cleared). Foreign writes drop the cached list; ours carry `Leviathan.FileClipboard`.
- **E5: Paste as shortcut / hard link / symbolic link stay disabled until Phase 2.** The spec lists them (§6.1) but link creation is not built; a disabled item with a tooltip is honest, a fake would not be. Paste into new folder works.
- **E5: hidden file views never scroll.** Both the Details and the List / Thumbnails views stay bound to every tab; a collapsed ItemsRepeater cannot create elements, so any scroll-to-selection while hidden is skipped and repeated when the view is shown.
- **F1: a stuck shell extension costs a thread, not the host, until there are too many.** A COM call into a hung handler cannot be cancelled or the thread killed safely, so a request over its limit is abandoned: the caller is told at once, a fresh STA thread replaces it, and the stuck one exits if it ever returns. Eight stuck threads end the process with exit code 2 and the supervisor starts a clean one (a crash-style restart, counted against the three-in-five-minutes rule).
- **F1: the time limit counts from when a thread starts the work.** Queue time is not the extension's fault, and a menu waiting behind another is still one person's click; the caller bounds the wait with its own token.
- **F1: STA threads rely on .NET's own pumping while idle and blocked.** Waiting on an STA thread dispatches COM calls and sent messages, which is what context-menu handlers need. A full message loop per thread is added only if a handler turns out to need posted window messages (checked on Brett's machine with 7-Zip, Git, VS Code in F2/F3).
- **F1: the host shares the worker's `ContractVersion`.** One number to bump and check, so a half-updated install says "restart Leviathan" for both processes. `PipeNames` gained the shell host prefix, an additive change.
- **F1: `--pipe <name>` starts a private host.** Tests run the real exe on their own pipe and mutex so they never meet, or kill, a real user's host.
- **F2: one thread per open menu, not the shared pool.** The handlers' COM objects live in the apartment that made them, so building, reading submenus, invoking and releasing must be the same thread, and it needs a message loop for dialogs and hidden windows. A menu therefore owns a `StaMessageThread` until it is closed. Files reuses warm workers; Leviathan starts cold and measures first (F3), because reuse brings back the problem of one handler poisoning later menus.
- **F2: the host returns every item; the UI filters.** Items Leviathan shows itself (Open, Cut, Copy, Paste, Rename, Delete, Properties) are dropped in F3 by verb, so the host stays a faithful window onto the shell and the policy lives with the menu design.
- **F2: an invoke that outlives 10 s is reported as started.** A verb that shows a dialog does not return until it closes; the caller must not wait on it, and the thread must keep running its loop. The menu is marked busy so the idle sweep leaves it alone.
- **F2: E_NOTIMPL from a handler is normal.** `HandleMenuMsg` and `GetCommandString` are optional and .NET raises E_NOTIMPL as `NotImplementedException`; both are caught where the shell may say no. Commands numbered above 5000 are not asked for a verb: a handler that returns a huge offset can cause an access violation, which .NET cannot catch (Files saw it with NVIDIA's item).
- **F2: contract minor 1.** Four new methods; same major, so an older host and a newer app still refuse each other only through the usual version check on the first ping.
- **F3: the menu never waits for the shell.** Leviathan's items are built and shown first; the shell's arrive later into a placeholder, and any failure (host down, disabled, slow, crashed) becomes one greyed line with the reason in its tooltip. This is the spec's "a slow extension never delays the menu" made literal.
- **F3: a menu that ran a command is not closed by the UI.** Closing it would queue behind a dialog the command may have opened and time out in the host; its idle sweep closes it after two minutes.
- **F3: right-click on empty space clears the selection.** Otherwise the menu would be the old selection's, which is not what Explorer does and not what the user pointed at.
- **F3: `ContextRequested` replaces `RightTapped`.** One event for mouse, touch, pen, the menu key and Shift+F10. With no pointer position the keyboard menu opens near the top of the list.
- **F3: the crash switch is a command-line option on the real host.** A real crashing COM handler would have to be built and registered system-wide; `--fault-crash-once <marker>` ends the host abruptly the first time a menu opens, which is what the app sees from a crashing handler.
- **F3: Shift+right-click inline items follow the shell's own order**, after Leviathan's items and a divider.
- **G1: built before I1–I10, as asked.** The plan puts tab groups (I4) and the status hub ahead of G1 so Last session carries them from the start. The session format is versioned JSON that ignores unknown properties and `TabState` / `SessionWindow` are records, so groups and hub state are additive; that work will extend `SessionCapture` and the tests.
- **G1: three files, not one.** Last session is rewritten every few seconds; named profiles and settings change rarely and must survive a crash during that write, so they live in `profiles.json` and `settings.json`.
- **G1: the last window closing saves, then freezes.** Each window closing would otherwise save a smaller session, and the last would save none. Closing one of several windows is a normal change and is saved. A capture with no tabs is never written.
- **G1: restored tabs are idle until shown.** `TabViewModel.Restore` does not list; the window lists a tab when it first binds it, so only the visible tab touches the disk or the network at startup, and an unreachable share becomes an offline tab with the usual fail-fast message.
- **G1: with "ask me", recording starts after the choice.** The window shown behind the question must not replace the session the user is about to pick.
- **G1: opening a profile into a running app opens its windows first.** The last window closing ends the app, so replacing must never pass through zero windows.
- **G1: `LEVIATHAN_DATA_DIR`.** Settings, Last session and profiles can be moved, which keeps test runs and a portable copy away from the real files.
- **I5: tab groups stay on WinUI `TabView`; the chip is an item of the strip.** The plan allowed either that or a custom strip. A custom strip would redo dragging, overflow, title-bar hit regions and tear-off that already work and are tuned against WinUI crashes (the strip comment about removing a tab under its own drag). A chip is a `TabViewItem` that is not closable and, when clicked, folds the group and returns the selection to the real tab; the group colour runs as a bar under each tab; a folded group's tabs are `Collapsed`. If the chip's selection flicker or its tab-like spacing is not good enough in daily use, the custom strip stays an option behind the same view-model.
- **I5: what a drag means is decided in the view model, given the item that was dragged.** `StripReorder.Decide` compares the strip's order with the model. A tab crossing a chip and a chip crossing a tab give the same result, so the dragged item is passed in; without it the logic guesses from whether the tab order changed.
- **I5: new groups ask for a name at once, and Skip is fine.** The spec says "name it inline"; a group with only a colour is a valid group (Edge does the same), so the dialog never blocks.
- **Large folders: rows reach the UI in a few updates a second, in chunks of at most 2,000.** Found with a 50,000-file folder (48,785 files, Details layout): every incoming batch (every 16 to 50 ms) re-merged and re-published the whole list, a Reset of the grid each time, and the end of every listing sorted all rows again on the UI thread. Now the first batch is shown at once (§3.1 first rows), later rows are gathered until an interval that grows with the folder (40 ms up to 400 ms, 50,000 rows about 200 ms), each UI callback takes at most 2,000 rows (about 20 ms of sorting and merging), and the folder only becomes Loaded when the last chunk is in. Measured on the local 50,000-file folder in the real app: the watchdog's worst stall went from 687 ms to 133 ms, UI updates from 44 to a few dozen small ones, the longest callback from 243 ms to 50 ms (one 118 ms at the start).
- **Applying an unchanged view does not sort again.** The end of every listing resolves the view again (folder type found); sorting 50,000 rows afresh for nothing was a single stall of several hundred milliseconds.
- **A mapped drive letter is a network location.** `Y:` pointing at a NAS used the local lister (small buffers, many round trips) and had no dead-share timeout; only UNC paths got the large-fetch Win32 lister. `MappedDrives` asks `GetDriveType` (no network traffic, remembered for 30 s) and the provider lists such drives like shares. The sidebar, drop rules and health tracking still treat a drive letter as local; to be unified with the network settings (I10).
- **Folder sizes stay as they are:** they start only after a listing finishes, run in the worker and never touch the UI thread, so they cannot be what blocks it. Their cost on a NAS (a recursive walk per visible folder) is a Quick settings question for I10.

- Listing cache (C1/C2): in-memory LRU by entry count (200,000), keyed by folder + hidden/system flags. A visit shows the cached rows at once and re-lists in the background, applying only the diff; a listing under 2 s old is trusted without a check. F5 on an already loaded folder and every reload after our own change bypass the cache. The footer says when rows are cached ("items may change"), then "Updated: …" for 6 s. Our own copy/move/delete/undo invalidate the folders involved, so other tabs never show them stale first.
- Folder watcher (C3): `IFolderWatcher` (Core) with `LocalFolderWatcher` (FileSystemWatcher, direct children only, 300 ms debounce, at most one report a second). Only plain local drives are watched; UNC, other network kinds and mapped drives are not (change events over SMB are unreliable and chatty), they are checked when visited. A report invalidates the cache entry and the view lists again behind the rows and applies only the diff, silently (no footer notice: the rows simply follow the disk); one check at a time, and a change during a load or check is re-checked when it ends. The watch starts off the UI thread.
- Saved listings (C4): `SqliteListingStore` in its own `listings.db` (not `leviathan.db`: it is disposable, so a damaged or wrong-version file is just recreated). One Brotli-compressed row per folder and hidden/system variant (about 70 bytes an item: 50,000 files is under 4 MB), 256 MB cap with least-recently-used eviction, rows not refreshed for 60 days dropped on open. Nothing is opened until the first folder is shown (cold start), all calls run off the UI thread, failures become IOException which the cache absorbs. An unchanged check only updates the saved time (`TouchAsync`) instead of rewriting the row. `ClearAsync` and `UsageAsync` are ready for the Quick settings / settings sheet (I10).
- Icons (I6, D33): the app asks for semantic keys (`IconCatalog`: 81 keys, each with a Segoe glyph fallback and a role colour such as red Delete); an icon pack is a folder of SVGs plus `pack.json` mapping keys to files, so a pack is data, not code. Two ship: Fluent UI System Icons (MIT, its own colour variants for Document, Cloud, Home and the rest recoloured by role) and Font Awesome Free 6.7.2 (CC BY 4.0, attribution in THIRD-PARTY-NOTICES.md). The pack is `Appearance.IconPack`, applies without a restart (Options > Icon set until the settings sheet, I10). `tools/icons/packs.json` + `Get-IconPacks.ps1` regenerate the packs at pinned versions; to add a pack, add an entry and run the script. Single-colour SVGs are recoloured in memory (`SvgTint`) for role and theme and drawn by `ImageIcon`/`SvgImageSource`; a key a pack lacks, and high contrast, fall back to the system glyph. Role colours belong to the catalog, not the pack, so swapping keeps their meaning. Menus and models that carry a Segoe glyph route through `IconCatalog.FindByGlyph`, which avoids naming a key at 40 call sites.
- File view (I6 follow-up): until real shell icons are wired, Details, List and Thumbnails rows draw folder, link and plain-file icons from the pack (one shared image source per icon, not one per row) and fall back to the system glyph without a pack or in high contrast; per-type shell icons (an .mp4 with its player icon) are a separate slice. Not yet switched: the sort arrows in the Details header, the Rename box, dialogs.
- Status hub (I7, D34): per-window `StatusHubModel` (tab, open, pinned, placement, size) in `WindowViewModel.Hub`, rules unit-tested: only an unpinned fly-up closes on Esc or a click outside (the status bar is excepted so its parts can toggle it); a docked or popped-out hub stays; the pop-out is remembered as a fly-up. Height is a fraction of the window body (40% default, 15-80%), right-dock width in pixels; both drag from the panel edge and are saved to `hub.json` shared by all windows (written 600 ms after the last change). The Operations tab lists the worker's operation-lane jobs (`OperationsModel`, fed by one hook on the lazily started worker connection, so opening the hub never starts it); background-lane jobs wait for the Background tab (I9). Failed jobs show a badge on the chevron until the Operations tab has been open. Activity, Background, Quick settings and Space tabs are placeholders naming the slice that fills them. Entry points: chevron, the operations chip, the free-space part (Space), Ctrl+Shift+O (`hub.toggle`). Row actions (pause, cancel, retry) and sparklines arrive with the Phase 2 operations engine.
- Activity log (I8, D35): `ActivityLog` listens to the command layer's `ActionTrail` (new `Recorded` event) and adds how our own copies, moves and deletes ended (one note per job from `AppHost`, so several windows never log it twice). Entries are worded by `ActivitySummary` (command id and target to "Renamed a.mkv"), classified for the filter, and kept in `activity.db` (own file, 7 days, nothing opened until first use); adding costs a lock and a list insert (< 1 ms, tested) and the store is written in one batch a second later off the UI thread. Window chrome (sidebar click, address focus, hub toggle, filter focus) is left out: the navigation a sidebar click causes is logged itself. Earlier sessions load only when the tab asks for them, so startup never waits. Undo is the global stack (only the last action can be undone), so the tab has one "Undo last" button rather than a button per row. Not yet linked: "open the related job" (log entries carry no job id yet; Phase 2's operations panel adds it), per-command argument summaries beyond the target (the registry records the target only; in-process parameters are deliberately not recorded).
- Bug found by running the app twice: a control in `StatusHubPanel` raised its change event while its XAML was still being built, and with the Activity tab remembered the handler read controls that did not exist yet, which killed the app at startup (stowed exception 0xc000027b). Handlers now wait until construction is done. A second launch with saved state is part of how a slice is checked from now on.
- Background tab (I9): `BackgroundModel` lists the worker's background-lane jobs (folder sizes today; probing, thumbnails and indexing join as they are built) running first, at most 40 rows plus a count line ("2 running · 19 queued · 6 finished in the last minute"), with Pause / Resume per job, Pause all / Resume all, and a priority box for jobs that can still be reordered; the thumbnail cache (held, bytes, being made, failed) and the worker and shell host (state, process id, restarts after crashes, "Switch back on" when disabled). `ProcessSupervisor` gained `RestartCount` and `ProcessId`. The tab polls every 2 s only while it is shown (the numbers have no event); job rows change on the worker's events. Lists are replaced only when they differ, so an open priority box is not closed under the user. Reading a process that was never started shows "Not started" rather than starting it. Media probing, indexing and contact sheets (Phase 3 and 4) add rows by emitting background-lane jobs; no tab change is needed.
- Seen while checking I9, not fixed here: opening `C:\Windows` made the worker count `C:\Users\Brett Baker\AppData` twice at once. Two requests for one folder should share one job.
- Settings sheet and Quick settings (I10, D36): the sheet rises over 70% of the window from Options (the gear is now a split button: click = settings, arrow = windows, profiles, diagnostics) or Ctrl+,; Esc clears the search first, then closes; a click on the dimmed rest closes it; it can fill the window. It is made the first time it is opened. Only settings that really do something are shown: General (startup mode and profile, where a new tab opens), Appearance (icon set; theme, density, accent and Mica arrive with G3 on this page), Files and folders (hidden, system, folder sizes), Tabs and windows (last tab), Advanced (settings file, diagnostics, clear caches). Pages for later phases list what they will hold and when, and the search finds those entries too, so nothing looks missing. Every control saves through the settings store at once and `AppHost.ApplySettings` applies it (hidden/system files both ways with the View menu, folder sizes, network sizes and thumbnails, last-tab rule, new-tab location, concurrency limits, icon pack); the worker gets the limits whenever it connects. Quick settings (status hub) holds how many operations, operations per drive and background jobs run at once and two switches for network drives (folder sizes, thumbnails; both default on, as the app behaved before). Polling interval and bandwidth limit are not shown as controls until Phase 2 gives them something to do. Settings the app does not use yet (single-click open, show extensions, Ctrl+Tab order) are kept in the file but have no control.
- Keyboard map (G2, spec 17.3): defaults completed for the Phase 1 commands (Ctrl+H hidden files, Ctrl+I invert, Ctrl+Shift+A select none, Alt+Enter properties on the one selected item) and a test ties them to the commands: every command's default shortcut is bound, every binding runs a real command, no key is bound twice. Enter is the exception on purpose: the file list raises it itself because it knows the row. The settings file's `KeyBindings` map a command id to one gesture; that gesture replaces all the command's default keys, empty text removes them, a key another command held moves to the named one, entries are applied in command-id order so the file's arrangement never matters, and a bad entry is reported and skipped. The Keyboard page of the settings sheet lists every command with its keys (a "changed" mark only when the keys really differ from the defaults), shows what was wrong in the file, and has "Read the file again" (`SettingsStore.ReloadAsync`), because the file is how keys are changed until the full remapping page (Phase 5: capture a key, import and export). Tooltips and menu hints still show the default keys. Keys of symbols (comma, minus, brackets and so on) can now be bound. Not verified by keyboard in the app: the test driver cannot deliver keys, so resolving a pressed key to a command is covered by the unit tests only.
- Appearance (G3, spec 17.2): the Appearance page of the settings sheet holds theme, density, accent colour, Mica, icon size and the icon set. Live: Mica (the window gets a plain background in the colour of its theme), density (Details rows 30 or 24 px, sidebar row padding), icon size of the file list (16, 20 or 24; a row is always tall enough for its icon), and the icon set. At the next start: the theme, because WinUI fixes the application's theme in its constructor and a window switched to another theme at run time keeps every colour that was looked up in code (about 16 places read brushes by name and draw them in the old theme), which left dark text on a dark window in testing. `ThemePeek` reads the one setting out of settings.json by hand before the application exists (a file of a few hundred bytes; the one deliberate synchronous read at startup). Also at the next start for the window that is open, but at once for any window opened afterwards: the accent colour. Putting the new accent's brushes into the application resources works for everything made afterwards; controls already on screen keep the brushes they resolved, and switching the theme away and back to make them read again left a mixed-colour window, so it is not done. What would close both gaps: replace those code-side brush lookups with brushes bound to the theme (one source of truth for sidebar, rows, address bar and notices), then live theme and live accent become safe. Accent shades are worked out from the colour (`AccentPalette`: lighter and darker steps; light themes use the darker fill, dark themes the lighter). A hand-edited file is cleaned on load (unreadable accent becomes "Windows", icon size becomes the nearest offered).
- Found on the way: the density radio buttons were written with Comfortable first but the enum starts with Compact, so each choice was saved as the other one. The mapping is now explicit, and a second launch with saved state again caught a startup problem (theme at startup) before it reached anyone.
- UI smoke tests (H1): `tests/Leviathan.UI.Tests` (FlaUI 5.0.0, MIT) start the real `Leviathan.exe` per test with its own `LEVIATHAN_DATA_DIR`, drive it with real mouse and keyboard input and read results back through UI Automation or the disk. The stall rule (spec 3.2) is enforced inside an `Acting()` window: any UI stall over 50 ms while the test clicks or types fails it, with the trace lines of the stall. Two things about measuring, learned the hard way: a UI Automation client walking a WinUI window's tree stalls it by itself for 300 to 500 ms (so elements are found before the window opens and checked after it closes, and acting uses plain mouse and keyboard input, which showed zero stalls for opening and closing the hub four times), and the text of the stall counter has to be read from an element found once. Finding that Ctrl+Shift+O does nothing on this machine: the key never reaches the app, because Claude's desktop app owns it as a global shortcut. It stays the default (spec 16.1) and can be changed in the settings file; the tests open the hub from the chevron.

- A1 (spec 3.5 item 5): server identity is decided by shared resolved addresses (DNS), not by an SMB negotiate query. It needs no extra protocol code, works for NetBIOS/DDNS/IP names alike, and is testable with a fake resolver. Risk: two names that share one address behind a proxy merge; a real SMB server-GUID check can be added behind the same `ServerIdentityMap` if the NAS lab run shows a miss.
- A2 (spec 3.3): health is fed by a decorator around the provider, not by each provider, so SMB, SFTP and the rest get it for free. Only UNC locations are tracked for now. `ShouldAttempt` can let several callers through at the moment a back-off ends (the tracker does not reserve the probe); harmless for listings, to revisit if probes ever cost something.
- B1 (spec 12.1): a rename is used only when both ends have the same literal share root; two names of one NAS (by identity) get server-side copy instead, because a rename across two spellings of a server is not guaranteed to work. Skipped files (Skip policy) are left out of the job's byte total rather than counted as done, so the progress bar ends at 100% of what was actually moved. The saved plan is not reused after a restart until B3 records per-file progress; replaying a plan whose moves already happened would fail on missing sources.
- B2 (spec 12.1, 3.5): unbuffered I/O is done in the portable copier (FileOptions.NoBuffering through IFileSystem) rather than in Windows-only code, so its alignment and last-sector logic is unit-tested on the mock file system and again on a real disk. Alternate streams that a destination cannot take do not fail the copy; they are counted in the result (data first, tags best effort). ACL copying is left out for now (optional in the spec). A server-side copy (CopyFile2) makes no hash, so a move done that way is checked by size until the verify policy (B4).
- B3 (spec 12.1 step 4): resume reuses the saved plan only when it was made for the same request (move/copy, conflict policy, destination, sources); numbered names chosen at plan time are therefore stable across a resume. The part file is kept on cancel and on transient network errors (so a resume can continue it) and removed on any other failure. Open: a user-cancelled job leaves its plan, journal and part file behind; they need a cleanup when a job is cancelled or removed (to do with B5/C1). A confirmed byte count is written every 32 MB or 2 s, so a crash loses at most that much work per file. CopyFile2 (server-side) is not restartable here and starts the file again.
- B4 (spec 12.1 step 6, 3.5 item 4): verification is decided per file by `VerifyPolicy.Decide`. A move to another volume is always verified, even with Verify=Off, because the source is deleted afterwards (nothing is ever lost outranks the setting). Hashing moved from SHA-256 to xxHash3 (already pinned, listed in the notices): it is not cryptographic, but the goal is catching bad writes, not attackers, and it keeps the CPU out of the way of a 1 GbE link. Sampled checks are probabilistic by design: damage outside the sampled blocks of a file over 4 GB is not seen; Verify=Full removes that limit.
- B5 (spec 12.2): invalid names are changed automatically when the destination is a network location, instead of asking per file. A copy of 5,000 files with a few bad names should not stop 5,000 times; the changes are listed in the job's report. Local destinations keep names as they are. A job that asks (OnError=Ask) stays Running with a prompt in its snapshot rather than getting a new state, so existing state handling is unchanged; the app uses SkipAndReport until the Operations panel (C3) can show the question, otherwise a job in a closed window could wait forever. The wait limit counts from the first drop and restarts if the job ran for over a minute in between.
